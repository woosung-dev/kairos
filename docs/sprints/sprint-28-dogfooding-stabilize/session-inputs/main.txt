[audit pattern 진화 — 본 sprint 부터 적용]

Sprint 27 의 핵심 학습 = **"audit ≠ dynamic verify"**. 정적 분석 4 sub-agent 가 audit 한계 안에서 GO 판정해도 진짜 dogfooding-blocker (dashboard 7.5s / JWT 1분 expiry / UX intent vs instinct gap) 는 catch 불가. PR #111 의 QA dynamic verify 가 처음으로 MCP Playwright + gstack browse 사용 → 3건 fix.

본 sprint 의 audit pattern 은 **3-Round 분리**:

**Round A (Static + Dep audit)** — 기존 Sprint 27e Round 1 pattern. 4 sub-agent (Security / Performance / Test-Coverage / Architecture) 병렬, file:line 증거.

**Round B (MCP Playwright runtime smoke)** — **신규 명시**. 본 sprint 부터 audit 의 필수 layer. 4 reviewer 가 자기 영역의 dynamic verify 진행.

각 reviewer 의 MCP Playwright runtime smoke 의무 항목:

- **Security**: live IDOR fetch (cross-workspace UUID tamper / JWT issuer tamper / cron token brute) + 보안 헤더 4종 live (curl + playwright network) + JWT cache DoS bench (1000+ tokens) + prompt injection 6s smoke (`?` mode RAG)
- **Performance**: dashboard 첫 진입 LCP/TTI (Lighthouse 또는 playwright network timing) + RAG p95 5 sample (실 사용자 시간) + 회의 업로드 5분 sample end-to-end + DB query 수 (BE middleware log) + Cloud Run cold start (재시작 후 첫 요청)
- **Test-Coverage**: e2e spec 실 실행 (CI 게이트 자체 + main 가지 history flake rate) + mutation test 최소 3 mutation (main.py 보안 헤더 / config validator / lazy seed) + 추천 권고 케이스 ROI 5건 신설 가능성 실측
- **Architecture**: runtime config verify (lifespan startup / env var loading) + 의존성 cycle runtime 검증 (실 import 시점 ImportError 회피 확인) + Sentry SKIP path 의 5xx forensic dump 확인

**Round C (Adversarial fuzz + production)** — Round 2 가 정적 추정만 한 영역의 실 verify. (선택 — 본 sprint 진입 신호 시)
