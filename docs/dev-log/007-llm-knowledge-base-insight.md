# ADR-007: LLM Knowledge Base 패턴 — Karpathy 워크플로우에서 얻은 인사이트

> **상태:** 연구 / 적용 검토 중
> **날짜:** 2026-04-04
> **출처:** Andrej Karpathy X 포스트 (2026-04-02)
> **관련:** Phase 4 (L3/L4 인사이트 + 프로액티브 알림)

---

## 1. 배경

2026-04-02 Andrej Karpathy가 공유한 **"LLM Knowledge Bases"** 워크플로우가 AI 커뮤니티에서 큰 반향을 일으키고 있다. 핵심 주장은:

> **"RAG(벡터 검색)에 의존하기보다, LLM이 직접 지식을 '컴파일'하는 마크다운 위키가 더 효과적이다"**

Karpathy는 최근 자신의 토큰 사용량이 코드 조작보다 **지식 조작**(마크다운 + 이미지 형태)에 더 많이 들어가고 있다고 밝혔다. LLM을 코딩 도구가 아닌 **개인 지식을 체계적으로 구축·관리하는 도구**로 전환하고 있다는 것.

---

## 2. Karpathy 워크플로우 4단계

### 2.1 Data Ingest (데이터 수집)
- 기사, 논문, 깃허브 레포, 데이터셋, 이미지 등을 `raw/` 디렉토리에 수집
- Obsidian Web Clipper로 웹 기사를 마크다운으로 변환
- 관련 이미지도 로컬에 다운로드 (LLM 비전 참조용)

### 2.2 Compile (LLM 컴파일) — 핵심 혁신
단순 인덱싱이 아니라, **LLM이 원본 데이터를 읽고 구조화된 위키를 "작성"**:
- 요약 생성
- 핵심 개념 식별
- 백과사전식 문서 작성
- 관련 아이디어 간 **백링크** 생성

### 2.3 Q&A (질의응답)
- 위키가 충분히 커지면(~100문서, ~40만 단어), LLM 에이전트가 위키 기반으로 질문 응답
- Karpathy는 처음에 RAG가 필요할 거라 생각했지만, LLM이 인덱스 파일과 요약을 자동 유지관리하면서 이 규모에서는 충분히 작동

### 2.4 Linting (건강 검사)
- LLM이 위키를 스캔하며 **불일치, 누락 데이터, 새로운 연결고리**를 찾는 품질 점검 패스
- AI가 스스로 지식의 품질을 점검하고 개선

### 피드백 루프
- 생성된 Q&A 출력물을 다시 위키에 "파일링"하여 추가 질의를 위해 지식 축적
- **쓸수록 더 똑똑해지는 구조** (복리 효과)

## 3. Kairos 현재 방식과의 대조

| 단계 | Karpathy 방식 | Kairos 현재 | 간극 |
|------|-------------|------------|------|
| **Ingest** | raw/에 기사·논문·코드 수집 | 회의 녹음 → STT → 트랜스크립트 | 유사 (입력 소스만 다름) |
| **Compile** | LLM이 위키 문서로 컴파일 (요약 + 백링크 + 인덱스) | Gemini가 요약·액션·태그 생성 → DB 저장 | **Kairos도 이미 하고 있지만, 출력이 DB 레코드지 "읽을 수 있는 위키"가 아님** |
| **Q&A** | 위키를 컨텍스트로 LLM에게 질문 | RAG 하이브리드 검색 → LLM 답변 생성 | **접근법이 근본적으로 다름** |
| **Lint** | LLM이 위키 품질 점검·보완 | ❌ 없음 | **Kairos에 빠져 있는 개념** |

### 핵심 차이: "컴파일"의 유무

현재 Kairos:
```
회의 → AI 요약(단발성) → DB 저장 → 끝
      ↑ 각 회의가 독립적으로 처리됨
```

Karpathy 인사이트 적용 후:
```
회의 → AI 요약 → DB 저장
                      ↓
        여러 회의를 종합 → "프로젝트 지식 문서" 컴파일
                      ↓
        새 회의 추가 시 → 기존 문서 업데이트 (점진적)
                      ↓
        Lint로 품질 점검 → 불일치/누락 발견 → 알림
```

**현재 Kairos의 AI는 "단발성 처리기"이지, "지식 컴파일러"가 아니다.**

## 4. Kairos 적용 분석

### 4.1 RAG를 버려야 하는가? → ❌ 아니다

| 비교 항목 | Karpathy | Kairos |
|----------|----------|--------|
| 사용자 | 개인 1명 | 팀 N명 |
| 데이터 규모 | ~100문서, ~40만 단어 | 수백~수천 회의, 수백만 단어 |
| 업데이트 빈도 | 자율적 (연구용) | 연속적 (매 회의마다) |
| 검색 요구 | 비동기적 (연구) | 실시간 ("이전에 이거 논의했나?") |

- **규모가 다르다**: 팀 데이터는 단일 LLM 컨텍스트에 절대 안 들어감
- **RAG 필요 이유**: 팀원 A가 참석하지 않은 회의 B의 특정 발언을 검색할 때, 컴파일 문서만으로는 원본 디테일을 못 찾을 수 있음
- Karpathy 본인도 "규모가 커지면 RAG 필요할 수 있다" 인정
- **결론: "RAG vs Compile"이 아니라 "RAG + Compile = 2-tier"가 정답**

### 4.2 적용할 것: "컴파일된 지식 레이어" 추가 → L3/L4 인사이트 구현 방법론

Kairos PRD의 Distill 단계:
```
L1: 개별 콘텐츠 요약 → ✅ 구현 완료
L2: 결정사항 + 액션 아이템 → ✅ 구현 완료
L3: 프로젝트 인사이트 (주간/월간 자동 종합) → ⬜ 미구현
L4: 조직 인사이트 (크로스 프로젝트 패턴) → ⬜ 미구현
```

**Karpathy의 "Compile"이 바로 L3/L4의 구현 방법론이다:**

```
매주 또는 매 N회의마다:
1. 프로젝트에 연결된 모든 회의 요약을 수집
2. LLM이 "프로젝트 상태 문서"를 컴파일
   - 핵심 결정사항 타임라인
   - 미해결 이슈
   - 진행 방향 변화
   - 반복되는 논의 패턴 (= Karpathy의 "백링크")
3. 이 문서를 RAG 인덱스에도 추가 (2-tier 검색)
4. 다음 컴파일 시 이전 문서를 업데이트 (점진적 증류)
```

### 4.3 적용할 것: "Lint" → 프로액티브 인사이트 구현

Kairos PRD에 이미 계획된 "프로액티브 인사이트 (AI가 먼저 알려줌)"의 구체적 구현:

| Lint 유형 | 구체적 예시 |
|----------|-----------|
| 결정 충돌 감지 | "3월 회의: A로 가자" vs "4월 회의: B로 가자" → 최종은? |
| 장기 미해결 감지 | 미해결 액션 아이템 2주 이상 방치 |
| 중복 논의 감지 | 같은 주제가 3회 이상 반복 논의 |
| 문서 갱신 필요 | 프로젝트 상태 문서가 최근 회의 내용 미반영 |

### 4.4 적용할 것: Q&A 피드백 루프 → 복리 축적

현재: 사용자 질문 → RAG 답변 → 끝 (일회성)
개선: 사용자 질문 → RAG 답변 → **답변을 프로젝트 지식에 재반영** → 다음 질문 시 더 정확

이것이 Kairos가 표방하는 **"복리 지식 축적"**의 실제 메커니즘.

## 5. 인사이트 신뢰도 평가

| # | 인사이트 | Kairos 적용 | 신뢰도 | 시기 |
|---|---------|------------|--------|------|
| 1 | **"지식 컴파일" → L3/L4 인사이트 구현 방법론** | 여러 회의를 종합한 프로젝트 지식 문서 자동 생성 + 점진적 업데이트 | ★★★★★ | Phase 4 |
| 2 | **"Lint" → 프로액티브 인사이트 구현** | AI가 지식 불일치·누락·중복을 감지하고 먼저 알림 | ★★★★★ | Phase 4 |
| 3 | **2-Tier 검색: 컴파일 문서 우선 → RAG 폴백** | 컴파일된 요약을 먼저 확인, 디테일 필요 시 RAG로 | ★★★★☆ | Phase 4 |
| 4 | **피드백 루프: Q&A 결과를 지식에 재반영** | 사용자 질문+답변을 프로젝트 지식에 축적 (복리 효과) | ★★★★☆ | Phase 4~5 |
| 5 | **Kairos = Karpathy가 말한 "제품화" 대상의 팀 버전** | 포지셔닝/마케팅 메시지에 활용 가능 | ★★★★☆ | 즉시 |
| 6 | **RAG를 버리고 Compile-only로 전환** | 팀 규모에서는 RAG 필수. 대체가 아닌 보완 | ★☆☆☆☆ | N/A |
| 7 | **Obsidian 연동 (마크다운 export)** | 있으면 좋지만 핵심은 아님 | ★★☆☆☆ | Phase 5+ |

---

## 6. 결론

> **Karpathy의 "LLM Knowledge Base"는 Kairos의 Phase 4 (L3/L4 인사이트 + 프로액티브 알림)를 어떻게 구현할지에 대한 방법론적 답이다.**

- **Compile** = Kairos의 "프로젝트별 종합 인사이트 자동 생성"
- **Lint** = Kairos의 "프로액티브 인사이트 (AI가 먼저 알려줌)"
- **피드백 루프** = Kairos의 "복리 지식 축적"

Karpathy 본인이 **"여기에 해키한 스크립트 모음이 아닌 놀라운 새 제품이 나올 여지가 있다"**고 말한 것은 Kairos의 방향성이 시장 타이밍과 맞다는 시그널이다. 다만 Kairos는 "개인 위키"가 아니라 "팀 세컨드 브레인"이므로, RAG를 버리는 것이 아니라 **RAG 위에 Compile 레이어를 얹는 하이브리드**가 정답.
