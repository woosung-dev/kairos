3. Critical / High 결함 상세

BUG-C01 — RAG `/rag/ask` 일부 입력에 500 응답 (graceful degrade 부재)

Critical

재현: prompt-injection 류 영문 + unicode 변형에서 첫 호출 500 → 두 번째 200 (cache hit). 응답 body `{"detail":"Internal Server Error"}` (영문).

Root Cause 가설: Gemini SafetyFilter `BlockedPromptError` 또는 빈 candidate 미catch. SemanticCache 오염 의심.

권고: ① `rag/service.py` Gemini 예외 catch → SSE error event 또는 200 + 한국어 안내. ② 입력 검증 (`min_length=1, max_length=500`, whitespace strip ≥2). ③ 5xx 발생 시 한국어 안내 메시지.

발견: Sentinel · 영향: 비용 abuse + 사용자 신뢰 손상 + Sentry 노이즈

BUG-H01 — Dashboard stale workspace_id 403 + setState-in-render

High

재현: 로그인 → dashboard 진입 시 `7aea8c86-...`(존재하지 않는 ws) 호출 2건 403. React 콘솔: "Cannot update a component (Header) while rendering a different component (DashboardPage)".

권고: `dashboard/page.tsx:78-82` setState를 useEffect로 이동. Header `useMembers(wid)`에 `enabled: workspaces.includes(wid)` 가드. 로그아웃 시 React Query 캐시 invalidation.

발견: Sentinel · 영향: React 19 strict 격상 시 throw 위험 + 무의미한 BE 부하

BUG-H02 — Visibility 모달 race condition (soft navigation 시 안 열림)

High

재현: 사이드바 "🚀 시작하기" 클릭 → "Visibility: 공개" 배지 클릭 → 모달 안 열림. F5 후 동일 클릭 → 정상 열림.

Root Cause: `useWorkspaceRole`이 첫 렌더에서 members 없이 평가 → role=null → canManage=false → onClick=undefined. 이후 onClick prop 갱신돼도 dialog mount 안 됨.

권고: `useWorkspaceRole`이 `{role, isLoading, canManage}` 반환. VisibilityBadge 클릭 핸들러는 `() => canManage && setOpen(true)` 패턴. 다른 권한 분기 컴포넌트도 audit.

발견: Sentinel + Casual (모바일에서 dropdown 안 보임으로 동일 결함 우회 발견)

BUG-H03 — 헌법 I-16 위반: PATCH /workspaces/{wid}/settings만 snake_case 강제

High

재현: `{"inboxThreshold":0.85}` body → 422. snake_case `inbox_threshold`만 통과.

Root Cause: `backend/src/workspaces/schemas.py:72-73` — `UpdateWorkspaceSettingsRequest`에 alias / `populate_by_name=True` 누락.

권고: alias 추가 + 전 backend schemas.py grep audit (`@field` / `Field(...)` 모두 점검) + schemathesis property test (V-T4) 도입으로 lock-in.

발견: Sentinel · 영향: I-16 헌법 위반, 외부 통합 시 혼란, schemathesis 실패

BUG-H04 — Meeting detail 응답의 `projects: []` 동기화 누락

High

재현: `POST .../meetings/{mid}/projects` 201 → 즉시 `GET .../meetings/{mid}` → `projects:[]`. 반대 방향 `GET .../meetings?projectId=...`는 정상.

권고: `MeetingService.get_detail`에 MeetingProjectLink join 추가 + 응답 schema에 채움. 또는 `projects` 필드 제거.

발견: Sentinel · 영향: meeting 상세에서 연결 프로젝트 노출 불가
