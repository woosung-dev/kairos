# AI 협업 세션 루틴

> AI와 협업할 때 매 세션마다 컨텍스트를 빠르게 동기화하고, 일관된 품질로 개발을 진행하기 위한 루틴.

---

## 핵심 요약: 매 세션 3줄

```
1. "PRD 읽고 현재 Sprint 확인해줘"          ← 방향 잡기
2. "[관련 문서] 읽고 [기능] 구현해줘"       ← 실행
3. "/qa" → "/ship"                          ← 마무리
```

## 0. 빠른 판단 요약

| 지금 상황                 | 명령                                                                                            |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| 세션 막 시작함            | `"docs/requirements/prd.md 읽고 현재 Sprint 상태 확인해줘. 지금 해야 할 작업이 뭔지 알려줘."`   |
| 뭘 해야 할지 알고 있음    | `"docs/architecture/erd.md 읽고 [기능명] 구현해줘"`                                             |
| 구현 끝남                 | `"/qa 실행해줘"` → (통과 후) `"/ship"`                                                          |
| 뭘 하고 있었는지 모르겠음 | `"docs/guides/development-methodology.md 읽고 지금 Stage 몇인지, 다음에 뭘 해야 하는지 알려줘"` |

## 1. 세션 시작: 방향 잡기

```
"docs/requirements/prd.md §5 읽고 현재 Sprint 상태 확인해줘.
 지금 해야 할 작업이 뭔지 알려줘."
```

**왜 필요한가:**

- AI는 매 세션마다 기억이 초기화된다 (메모리 시스템이 있지만 작업 상세는 저장하지 않음)
- PRD의 §5(Phase 로드맵)를 읽으면 AI가 **전체 프로젝트 맥락 + 현재 진행 상태**를 한 번에 파악
- "다음에 뭘 해야 하는지"를 AI가 판단해주므로, 매번 작업 목록을 기억할 필요 없음

**실제 동작:**

1. AI가 `prd.md`를 읽음
2. Sprint 별 완료/미완료 항목을 확인
3. 우선순위에 따라 "지금 해야 할 작업"을 제안

---

## 2. 기능 구현: 관련 문서 지정 + 실행

```
"docs/architecture/erd.md 읽고 [기능명] 구현해줘"
```

**왜 관련 문서를 지정하는가:**

- AI가 **추측 대신 설계 문서를 근거로** 코드를 작성하게 된다
- 예: ERD를 읽으면 테이블 구조, 관계, 필드명을 정확히 알고 구현
- 문서 없이 "구현해줘"만 하면 AI가 임의로 스키마를 만들 위험이 있음

### 상황별 지정 문서

| 상황               | 지정할 문서                                  |
| ------------------ | -------------------------------------------- |
| DB/모델 관련 구현  | `docs/architecture/erd.md`                   |
| AI 파이프라인 작업 | `docs/architecture/ai-pipeline.md`           |
| RAG 기능 구현      | `docs/architecture/rag-pipeline.md`          |
| 크로스 도메인 연동 | `docs/architecture/cross-domain-pipeline.md` |
| UI/UX 구현         | `docs/requirements/` 내 해당 스펙            |
| PARA 관련          | `docs/requirements/para-methodology.md`      |

**핵심 원리:** CLAUDE.md의 "Plan Before Code" 규칙과 연결된다. AI가 코드 작성 전에 설계 문서를 참조하게 강제하는 것.

## 3. Sprint 마무리: QA → Ship

```
"/qa 실행해줘"
→ (QA 통과 후)
"/ship"
```

**`/qa`가 하는 일:**

- 웹 앱을 체계적으로 테스트 (페이지 탐색, 폼 테스트, 에러 확인 등)
- 버그를 발견하면 소스 코드에서 직접 수정
- 수정 후 재검증까지 반복

**`/ship`이 하는 일:**

- base 브랜치 감지 & 머지
- 테스트 실행
- diff 리뷰
- VERSION 범프 + CHANGELOG 업데이트
- 커밋 → 푸시 → PR 생성

**순서가 중요한 이유:** QA를 먼저 해서 버그를 잡고, 깨끗한 상태에서 ship하면 PR 리뷰가 수월해진다.

## 4. 방향을 잃었을 때: 방법론 문서 참조

```
"docs/guides/development-methodology.md 읽고
 지금 Stage 몇인지, 다음에 뭘 해야 하는지 알려줘"
```

5-Stage 개발 방법론(Upload → STT → AI처리 → Inbox → 임베딩)과 Phase별 진행 방식이 정리되어 있어, 큰 그림에서 현재 위치를 파악할 수 있다.

---

## 왜 이 루틴이 효과적인가

```
전통적 방식:                    이 루틴:
├── 코드 열어봄                 ├── PRD로 방향 잡기 (30초)
├── "뭐 하고 있었지..."        ├── 문서 지정 + 구현 (정확)
├── 이전 작업 기억 더듬기       ├── /qa로 품질 검증
├── 임의로 구현 시작            └── /ship으로 배포
└── 나중에 문서와 안 맞는 걸 발견
```

**한 줄 정리:**

- **PRD = 나침반** — 어디로 가야 하는지
- **아키텍처 문서 = 지도** — 어떻게 가야 하는지
- **/qa + /ship = 체크포인트** — 제대로 갔는지 확인

## 8 Stage 방법론, 내가 알아야 할 것은?

> 상세: `docs/guides/development-methodology.md` (8 Stage 프레임워크)

### 8 Stage를 다 외울 필요 없다

사용자 입장에서는 **3가지 모드**만 구분하면 된다:

```
1. 설계 모드 (Stage 1~3) — "아직 코드 안 짬. 문서/디자인 만드는 중"
2. 구현 모드 (Stage 4~5) — "코드 짜는 중"
3. 마무리 모드 (Stage 6~8) — "다 짰고, 검증/배포/정리"
```

### 내가 알아야 하는 것 vs AI에게 맡기는 것

| 내가 판단                                | AI가 처리                                           |
| ---------------------------------------- | --------------------------------------------------- |
| 지금 어느 모드인지 (설계? 구현? 마무리?) | 구체적 명령어 (`/qa`, `/ship`, `/design-review` 등) |
| Sprint 목표가 뭔지 (뭘 만들고 있는지)    | 파일 경로, 의존성 분석, 코드 작성                   |
| 결과물이 맞는지 최종 판단                | Stage별 세부 절차와 순서                            |

### 왜 모드 감각이 필요한가?

AI가 "구현하겠습니다"라고 할 때, 아직 설계가 안 끝났으면 "아직 설계 안 끝났는데?"라고 브레이크를 걸 수 있어야 한다. **방향은 내가 잡고, 실행은 AI가 한다.**

### AI가 방법론을 자동으로 아는가?

- `CLAUDE.md` → **매 세션 자동 로드** (워크플로우, 스택, 현재 상태)
- `development-methodology.md` → **자동 로드 안 됨**, 요청해야 읽음

그래서 세션 시작 시 이렇게 하면 가장 정확하다:

```
"docs/requirements/prd.md 읽고 현재 Sprint 확인해줘.
 docs/guides/development-methodology.md도 참고해서
 지금 어떤 Stage인지, 다음에 뭘 해야 하는지 알려줘."
```

PRD(무엇을) + 방법론(어떻게)을 둘 다 참고해서 안내받을 수 있다.
